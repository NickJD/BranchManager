# BranchManager: GitHub Actions and GitHub Pages setup

This guide configures three workflows:

1. **CI** — runs the dashboard/reporting regression tests and Python syntax checks on pushes and pull requests.
2. **Dashboard deployment** — regenerates the interactive demonstration from the committed synthetic fixtures and publishes the `docs/` site to GitHub Pages.
3. **Release build** — builds wheel and source distributions and attaches them to a GitHub Release when a matching version tag is pushed.

The dashboard is generated by the actual `branchmanager.reporting.write_performance_review_dashboard()` function. The demonstration data are synthetic; no real partner or isolate data are used.

## 2. Commit and push the files

From the repository root:

```bash
git status
git add .github/workflows docs scripts tests/test_demo_dashboard_build.py README.md
git commit -m "Add automated dashboard demo and GitHub Actions"
git push origin main
```

If your default branch is not `main`, change `main` in the workflow trigger definitions to your actual default branch before committing.

## 3. Configure GitHub Pages (required once)

On GitHub:

1. Open the `NickJD/BranchManager` repository.
2. Go to **Settings → Pages**.
3. Under **Build and deployment → Source**, select **GitHub Actions**.
4. Save if GitHub presents a Save button.

Do not select “Deploy from a branch”. The workflow uploads the generated `docs/` directory as a Pages artifact and deploys that artifact.

The expected public URLs are:

- Documentation root: `https://nickjd.github.io/BranchManager/`
- Interactive dashboard: `https://nickjd.github.io/BranchManager/demo/`

The `docs/demo/index.html` file redirects to the generated dashboard HTML. The dashboard itself remains a normal, scrollable web page.

## 4. Check Actions permissions

Open **Settings → Actions → General**.

- Ensure Actions are enabled for the repository.
- The workflows declare their own minimum `GITHUB_TOKEN` permissions.
- The Pages deployment job needs `pages: write` and `id-token: write`; these are declared in `deploy-demo.yml`.
- The release workflow needs `contents: write` to create a GitHub Release and upload distribution files; this is declared in `release.yml`.

You do not need to create a personal access token or add repository secrets for these workflows. They use GitHub's automatically provided `GITHUB_TOKEN`.

If your organisation applies a restrictive Actions policy, an administrator may need to allow the listed `actions/*` and `softprops/action-gh-release` actions.

## 5. What each workflow does

### CI — `.github/workflows/ci.yml`

Runs on:

- pushes to `main`;
- pull requests;
- manual dispatch from the Actions tab.

It installs BranchManager, runs the dashboard/reporting regression tests and checks Python syntax. It does not publish the website.

The initial CI gate deliberately targets the dashboard/reporting tests because the broader repository test suite has known failures in other areas. Do not interpret this targeted green check as proof that every BranchManager workflow has passed. Expand the CI test command as those other failures are resolved.

### Dashboard deployment — `.github/workflows/deploy-demo.yml`

Runs when relevant dashboard/reporting code, demo documentation, demo fixtures, or the builder script are changed on `main`. It can also be started manually.

The workflow:

1. checks out the repository;
2. installs BranchManager;
3. regenerates `docs/demo/performance_review_dashboard.html` from the committed synthetic TSV/JSON fixtures;
4. builds a second copy in a temporary directory and validates the generated HTML and embedded data;
5. uploads `docs/` as a Pages artifact;
6. deploys the artifact to GitHub Pages.

The generated dashboard is not committed back to `main`. It is regenerated in the Actions runner and published directly. This avoids automated commits, merge conflicts and workflow-trigger loops.

The committed TSV/JSON files are the demo inputs. If the dashboard schema changes, update those fixtures and the builder/test as required. If only the reporting code changes, the same fixtures are used to regenerate the dashboard with the new reporting implementation.

### Release build — `.github/workflows/release.yml`

Runs only when a tag beginning with `v` is pushed. It:

1. checks that the tag version matches `[project].version` in `pyproject.toml`;
2. builds the wheel and source distribution;
3. creates a GitHub Release and attaches the files in `dist/`.

It does **not** publish to PyPI. That is intentionally separate because PyPI publishing requires a deliberate trusted-publisher configuration and should not be coupled to every GitHub Release by default.

## 6. Run the dashboard build locally

Use Python 3.12 or newer, consistent with the package metadata.

From the repository root:

```bash
python -m pip install -e .
python scripts/build_demo_dashboard.py
```

The generated file is:

```text
docs/demo/performance_review_dashboard.html
```

To run the build and validation without changing the committed demo output:

```bash
python scripts/build_demo_dashboard.py --check
```

The script reports the number of synthetic isolate records and the HTML file size. It fails if required fixture files are missing, expected dashboard sections/controls are absent, or the embedded JSON payload is invalid or empty.

## 7. Run the workflows manually

1. Open the repository's **Actions** tab.
2. Select **Build and deploy BranchManager documentation and dashboard**.
3. Select **Run workflow**.
4. Choose `main` and start the run.
5. Wait for both the build and deployment jobs to complete.
6. Open the Pages URL shown in the deployment job.

The CI workflow can be run in the same way by selecting **BranchManager CI**. The release workflow is tag-triggered; it is not a manual deployment workflow.

## 8. Configure a required CI check for pull requests (recommended)

After the first successful CI run:

1. Open **Settings → Rules → Rulesets** (or **Settings → Branches**, depending on the repository interface).
2. Create or edit the ruleset for `main`.
3. Enable the requirement for status checks before merging.
4. Select the check named **Dashboard and core reporting tests** (the job name in `ci.yml`).
5. Save the ruleset.

Do not make the Pages deployment workflow a required pull-request check: it only publishes from `main` and is not intended to run for pull requests.

## 9. Creating a GitHub Release

First update the version in `pyproject.toml` and `src/branchmanager/__init__.py` so they agree. Commit and push those changes to `main`.

Then create and push a matching tag:

```bash
git tag v1.0.1
git push origin v1.0.1
```

Replace `1.0.1` with the version you have actually set. The workflow intentionally stops if the tag and `pyproject.toml` version disagree. It then creates a GitHub Release with the built `.whl` and `.tar.gz` files attached.

## 10. Troubleshooting

| Symptom | What to check |
|---|---|
| Pages deployment reports that Pages is not enabled | Set **Settings → Pages → Source** to **GitHub Actions**. |
| Workflow cannot deploy Pages | Check the `pages: write` and `id-token: write` permissions in the deploy job and any organisation-level Actions restrictions. |
| Dashboard build says fixtures are missing | Confirm that the complete `docs/demo/assessment/` and `docs/demo/taxonomy/` directories were copied and committed. |
| Dashboard builds but the public page is missing | Check that `docs/demo/index.html` exists and the deployment artifact contains the `docs/` directory. |
| The release workflow rejects the tag | Ensure the tag without its leading `v` exactly matches `project.version` in `pyproject.toml`. |
| A dashboard update does not trigger deployment | Check the changed file against the `paths` list in `deploy-demo.yml`, or run the workflow manually. |
| The CI check passes but another BranchManager workflow is broken | The initial CI gate is intentionally limited to dashboard/reporting tests; it is not yet a full-suite green status. |

## 11. Recommended next step: broaden CI coverage

The current CI workflow provides a stable reporting/dashboard gate. As the remaining test failures are resolved, add the corresponding tests to the `pytest` command in `ci.yml`. In particular, the taxonomy, pangenome eligibility, marker QC, Sanger Studio, genome evidence and CLI workflows should ultimately have dedicated regression coverage.

Keep the public dashboard synthetic. It should demonstrate the reporting interface and schema, not expose partner metadata, isolate identifiers, sequences or project results.
